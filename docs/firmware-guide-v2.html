1. Scope and evidence

This guide explains how to develop, build and validate PCIe endpoints on Artix-7 FPGA boards. It covers platform identification, configuration space, host integration, DMA correctness, interrupts, reset behavior, HDL quality, Vivado builds, flashing and measured verification. It is an engineering reference, rather than a description of a particular commercial firmware.

The useful target is a documented interface contract. State the registers, operations, limits and reset behavior that your own design implements. A product name, a configuration-space dump or a passing benchmark cannot establish complete behavioral equivalence with another device. Avoid blanket claims such as "1:1", "universally compatible" or "guaranteed stable" without an explicit definition and supporting tests.

Use four evidence labels

  • Specified: required by the relevant protocol or vendor documentation.
  • Implemented: present in the source, with a stated build configuration.
  • Simulated: exercised by a named simulation or offline test with a recorded result.
  • Hardware-verified: observed on identified hardware, software and workloads.

These labels are not interchangeable. A module in a source tree might be disabled or disconnected in the shipped build. A passing unit test does not verify board wiring. A successful boot does not establish sustained DMA correctness. A simulation that bypasses the packet interface cannot prove that interface's framing and backpressure behavior.

Record failures and untested conditions alongside successes. Where a behavior is only observed on a single host, say so. A useful engineering note explains what was tested, what the result establishes and what remains unknown.

Read this guide in order

Beginners should complete Chapter 3 before changing endpoint behavior. Engineers investigating a regression can start with Chapter 16, then use the acceptance matrix in Chapter 15. Public references are collected at the end. Documentation for the exact FPGA, board revision and IP version takes precedence over examples here.

2. Hardware, topology and compatibility

Separate the host role from the operator role. The host contains the FPGA card in a PCIe slot and enumerates its endpoint. The operator runs the build, programmer and any supported external management tools. Two physical machines make recovery and observation easier, but the transport layout remains board-specific.

Do not infer transport wiring from a USB-C connector. That connector describes a physical form, not whether it carries a programming interface, data transport, both, or power only. Some boards have separate programming and data ports. Check the board documentation and labels before connecting cables or installing a driver.

Identify the complete target

  • FPGA family, exact part, package, speed grade and board revision.
  • Reference clock, pin assignment, PCIe lane wiring and reset wiring.
  • Flash part, density, interface width, configuration voltage and boot mode.
  • Programming adapter and data-interface hardware, including the appropriate drivers.
  • Host motherboard, CPU, slot, BIOS version, operating-system build and active driver.

A 100T image is not a substitute for a 75T image. Two boards using the same FPGA can still need different constraints and programming procedures. A larger connector does not establish the negotiated link width. Slot lane sharing and firmware policies can change device behavior without changing the endpoint image.

An engineering design's possible FPGA targets are separate from a commercial product's supported targets. Check current product support before purchasing a board. This guide does not certify compatibility for any particular board or motherboard.

Keep a recovery path

Retain a known working image for the exact board and a supported way to program it. Confirm the recovery procedure before testing a new image. Insert or remove a PCIe card only using the platform's documented procedure; ordinary desktop slots should not be treated as hot-plug slots.

Start with a short workspace path and a known project toolchain. Select the Vivado version required by that project, then verify device and IP support in that release. Do not assume every device, configuration or third-party programmer is covered by one licensing statement.

3. First build: establish the loop

The first milestone is a traceable edit-build-program-observe loop. Use a documented board project with a known test interface. Keep the initial change small enough that you can explain exactly what it should alter.

Baseline procedure

  • Record the board and host details from Chapter 2. Save existing device and driver information.
  • Obtain the source from its official repository and record the commit. Read its build and licensing instructions.
  • Open the exact board project. Build the unchanged baseline with its required toolchain.
  • Review synthesis, implementation, DRC, timing and clock-domain reports. Resolve relevant critical warnings.
  • Record the output hash and associate it with the source commit and build settings.
  • Program using the board's documented procedure. Verify the programming result.
  • Reload the FPGA using the documented reset or power sequence. Confirm the running build identity.
  • Exercise the project's documented host interface and save the result.

Use a designated firmware build identifier or test register for the next controlled change. Avoid arbitrary edits to identity, BAR, capability or reserved fields just to make an output different. Change the build identifier, rebuild, reload and verify the new identifier from the host. This tests the loop without introducing unrelated protocol changes.

Stop at the first failed stage

If the programmer cannot identify the board, do not debug host DMA first. If the baseline does not enumerate, investigate power, wiring, clock, reset, constraints and configuration. If enumeration succeeds but the driver will not start, inspect device resources and driver binding before running a throughput test.

Record both the expected and actual result. When a step fails, preserve its log before rebuilding. Change one variable at a time and compare against the baseline on the same host and slot. A clean baseline makes later regressions easier to isolate.

4. Configuration space as an interface

Configuration space describes a function's identity, resources and supported capabilities. PCIe provides an extended configuration-space address range, while the accessible extent and implemented structures must be determined for the particular function and access method. The familiar Type 0 header is only the beginning of the interface.

Separate static declarations from host-programmed control and live status. Vendor and device identifiers are declarations. BAR addresses are allocated by the host. Command bits change during enumeration and driver operation. Link status must represent actual negotiated conditions rather than a static maximum copied from a template.

Build a register contract

For each implemented field, record its offset, width, reset value, access type, supported byte enables, update owner and behavior across reset. Distinguish read-only, read/write, write-one-to-clear and other side-effect semantics. Follow the applicable specification for reserved fields; do not apply a blanket zero-fill rule to every unclassified byte.

Do not use another device's identifiers to imply compatibility with its driver. A driver needs the actual register and transaction behavior it expects. For a new design, use appropriately assigned identifiers and a driver that implements the intended interface.

BARs need real behavior

BAR type, width, size and decode behavior must agree. A 64-bit memory BAR consumes a pair of header entries. A resource-size probe is not a normal address assignment. Check address alignment, byte enables, upper address bits and accesses at the edge of the region. Do not advertise a resource without implementing its required behavior.

Configuration handling may be split between hard IP and application logic. Establish which path owns each field. A shadow image does not automatically replace values handled by the core. Verify the host-visible result after enumeration, then compare writable fields according to their semantics instead of expecting a byte-identical startup dump.

5. Capabilities, interrupts and power state

Capabilities declare functionality. Their presence requires the associated controls, state transitions and resources to work. Never populate a structure solely because it appeared in a starter template. Capability offsets and ordering are not universal constants.

Validate both lists

  • For conventional capabilities, check the list-present indication, pointer alignment, structure bounds, next pointers and termination.
  • For extended capabilities, check headers, supported versions, next-pointer bounds, overlap and termination.
  • Detect loops and duplicate or conflicting structures in offline validation.
  • Check that every advertised feature is supported by both the selected IP configuration and surrounding logic.

The interpretation of an extended region depends on the device and access result. An all-ones read can indicate an inaccessible or absent target, rather than a meaningful capability. Preserve the access error alongside the data.

MSI, MSI-X and INTx are distinct

MSI and MSI-X use different host-programmed mechanisms. INTx Disable in the PCI Command register controls legacy interrupt signaling; it is not the MSI Enable bit. Verify each supported mode independently. The 7-Series interrupt request and acceptance interface is documented in PG054 [R3]. Do not assume a one-cycle request is accepted without the corresponding handshake.

Use one clear owner for pending interrupt state. Test masked events, delayed acceptance, multiple events, acknowledgment and reset. The interrupt should represent an event defined by the device contract. Arbitrary periodic interrupts are not a substitute for correct command completion, and no generic heartbeat period makes an endpoint conformant.

Power and reset need observations

Advertise only the power and reset mechanisms that the design supports. Record behavior through driver start/stop, supported suspend/resume and documented reset operations. Do not assume that every link transition erases the function address or that a permanently sticky address is correct across re-enumeration. Follow the core's configuration and reset rules.

6. DMA addresses and IOMMU behavior

CPU virtual addresses, CPU physical addresses and device-visible DMA addresses are different concepts. A device must use the addresses supplied through its driver and DMA mapping interface. They need not equal host physical addresses. The Linux DMA API guide illustrates these address spaces and their mappings [R4].

IOMMU availability in BIOS is not a per-device access guarantee. Driver mappings, platform policy and device topology determine which transactions can succeed. Correct endpoint behavior includes obeying valid mapping lifetimes and stopping work before resources are revoked.

Windows distinctions

Kernel DMA Protection does not require VBS. A hypervisor-running flag does not establish the complete remapping state of a specific device. Microsoft documents Kernel DMA Protection and driver remapping separately [R1, R2]. Driver opt-in mechanisms also differ by Windows generation; use documentation for the actual installed release.

Keep these observations separate: firmware settings, the Windows security report, driver support, device enumeration and the outcome of a mapped DMA operation. None alone proves unrestricted memory access. Secure Boot and TPM settings are not substitutes for measuring the DMA path.

Troubleshoot the transaction

For a fault, preserve the event provider, ID, full XML, timestamp, platform details and the device location. Correlate the reported requester with the actual function before assigning responsibility. Decode reason fields using documentation applicable to that platform and event schema. One fault does not establish a unique firmware defect.

Use a test driver that maps a bounded test buffer and reports completion and data validation. Investigate invalid addresses, stale descriptors, mapping lifetime, reset and driver compatibility. A public guide should not prescribe disabling host protections or applying registry opt-outs as a general compatibility fix.

7. Transaction and completion correctness

DMA engines must obey the selected core interface and the PCIe transaction rules. Treat packet format, request tracking, data integrity and recovery as separate verification targets. A transfer that reaches the expected address can still have incorrect byte enables, residual length or completion handling.

Track each request

Maintain enough state to match returned completions to outstanding work. Validate supported address width, requested length, tag availability and expected completion bytes. Exercise split completions and malformed, unexpected or late responses in simulation. Verify that errors cannot accidentally retire an unrelated request.

Scatter/gather transfers must follow the descriptor contract. A buffer length of one page or less does not guarantee that one descriptor is enough. Conversely, a descriptor need not correspond to exactly one CPU page. Validate each descriptor's length, address, alignment and remaining transfer bytes rather than deriving descriptor count from an arbitrary transfer-size threshold.

Bound and test the datapath

  • Follow the applicable payload, read-request and boundary rules.
  • Handle first and last byte enables, short transfers and unaligned requests if supported.
  • Test upper address bits and supported 32-bit and 64-bit addressing paths.
  • Preserve packet boundaries while arbitrating multiple transmit sources.
  • Check returned length and content, not only a success indication.

A timeout is an error-handling transition. It is not permission to declare success, reuse a tag while an earlier request can still complete, or discard a descriptor silently. Recovery must account for outstanding traffic and the host's view of the operation.

Counters should distinguish accepted work, completed work, errors and retries. A high count of register accesses does not establish a high count of successful data transfers. Hardware conclusions should include the actual operation totals and failure totals.

8. HDL ownership, CDC and reset

Give each sequential state element one procedural owner. Use always_ff where supported and inspect synthesis and lint diagnostics. Multiple procedural writers are a design defect; do not rely on a tool to select a particular writer or claim that every tool silently handles them the same way.

Combine concurrent updates deliberately

A register can receive a host write and a hardware event during the same cycle. Compute one next-state value with an explicit priority. For an abstract set/clear register, a set-dominant example is:

always_comb begin
    next_flags = (flags & ~clear_mask) | set_mask;
end
always_ff @(posedge clk) begin
    if (reset) flags <= '0;
    else       flags <= next_flags;
end

This is a teaching example, not a universal register rule. Some interfaces require different event and acknowledgment precedence. Define the required priority, then simulate simultaneous events and confirm that no work is lost or completed twice.

Cross clock domains using a protocol

Synchronizers for single-bit levels do not make a multi-bit bus coherent. Use an appropriate handshake, asynchronous FIFO or vendor-supported CDC primitive. Check pulse capture, data stability, reset ordering, FIFO pointer crossing and the behavior when one clock stops.

Reset assertion and release must match the requirements of each domain and primitive. AMD's startup guidance explains why unsynchronized release can leave state inconsistent [R6]. Document which state survives each reset and which outstanding operations are invalidated. Test reset while idle, under backpressure and during a transfer.

Debug logic changes the implementation. Recheck timing, utilization and hardware behavior after adding it. Use bounded capture and clear ownership of counters rather than assuming diagnostic signals have no cost.

9. Queues, FIFOs and backpressure

A FIFO solves a bounded buffering problem. It does not make an indefinitely slower consumer keep up. Work out average and worst-case producer rates, consumer rates, burst size and maximum stall duration before selecting depth.

Track occupancy, overflow attempts, underflow attempts and stall duration in simulation. A protocol-correct producer must respect the consumer's ready/valid or equivalent contract. Confirm how the chosen FIFO indicates when output is valid; standard-read and first-word-fall-through modes are not interchangeable.

Width conversion needs consistent capacity

For an asymmetric FIFO, input depth and output depth are generally different. Compare total bit capacity and the legal ratios supported by that specific IP configuration. Do not force equal depth numbers just because both fields are called depth. Regenerate IP after changing width, depth, memory implementation or output mode.

Arbitration must preserve progress

Packet arbitration must hold ownership through the required packet boundary. Test long packets, a permanently busy source, short high-rate traffic and downstream stalls. Fairness and latency requirements should be explicit. Fixed delays inserted between requests can conceal a saturation problem without proving a robust design.

Buffer growth also consumes RAM and routing resources. A successful larger-device implementation does not prove that a smaller-device port can retain the same depths. Re-budget the design, regenerate the relevant IP and rerun functional and hardware acceptance when porting between parts.

Use a stress test that forces queue occupancy toward its maximum while preserving a deterministic expected data pattern. Check the final data, counters and recovery state after the stress phase. A display that continues to refresh is not sufficient proof that the transport never lost or duplicated work.

10. Class interfaces: implement what you declare

A PCI class code identifies an interface family. The host driver still expects that family's register semantics, descriptors, ordering, completion indications and error handling. Matching a class code or loading a driver is not a functional implementation.

AHCI is one public example of a standardized class interface. Its specification defines register and command structures [R7]. It can be studied independently of any commercial product. This guide does not prescribe a particular endpoint class or describe a proprietary data path.

Use a conformance checklist

  • Enumerate the implemented operations and any explicitly unsupported operations.
  • Define reset state, legal transitions, access widths and side effects.
  • Specify how commands reference buffers and how completion is reported.
  • Define byte-count accounting and error behavior for partial or failed transfers.
  • Test cancellation, reset, overlap and resources that become unavailable.

Never report successful completion for an unsupported command merely to stop a driver timeout. Never report a successful write while discarding data unless the published interface explicitly defines that behavior. A successful completion is a commitment to the interface's semantics.

Host-side caching can hide defects. Repeated file reads may be served without another device transaction. A read-after-write check establishes only what its access path actually reaches; a persistence claim needs a defined flush, reload or power-loss test and a known data-integrity result.

Do not turn a one-machine filesystem or driver observation into a universal rule. A read-only volume can result from policy, media state, filesystem damage, driver behavior or incorrect transfer handling. Preserve the evidence before changing metadata. Do not zero partition fields, initialize disks or delete driver caches as a general troubleshooting recipe.

11. Vivado builds that can be reproduced

Keep a source of truth for HDL, constraints, IP configuration, initialization files and build scripts. Record the exact FPGA part and Vivado release. Generated project copies must not become an undocumented second source of truth.

Build manifest

  • Source revision and dirty-worktree state.
  • Target part, top module and enabled build parameters.
  • Constraints and initialization-file hashes.
  • Tool and IP versions, implementation strategy and build command.
  • Build-log locations, final report results and output hashes.

Use a shallow workspace path on Windows. Check where Vivado actually resolves each referenced file. When editing a memory initialization file, confirm the active IP property points to that file, then regenerate the affected outputs using the documented flow. If an output seems stale, investigate the dependency before deleting directories.

Archive important logs first. A clean build belongs in a disposable, explicitly identified build directory; source files, captured evidence and recovery images should not be stored only inside it. Do not copy a blanket recursive deletion command into an unfamiliar project.

IP changes are interface changes

Changing FIFO mode can alter ports and read latency. Changing memory options can alter resource mapping and timing. Review the generated interface and simulation model, then update and test the wrapper. An encrypted-IP error is not by itself a diagnosis: inspect earlier messages for parameter, licensing, version and elaboration failures.

An artifact hash identifies exact bytes. A source manifest identifies build inputs. Neither replaces the other. A different hash does not prove a particular source change took effect, and a repeated hash does not by itself prove a cache bug. Confirm the intended running build identifier and test the changed behavior.

12. Timing closure and implementation quality

Timing analysis is meaningful only when the intended clocks and paths are constrained. Review clock definitions, generated clocks, I/O constraints, clock relationships and exceptions alongside setup and hold results. Check pulse-width and recovery/removal requirements where applicable.

An unconstrained path is not a passing path. AMD documents that such paths are not timed because constraints are missing [R5]. Review check_timing, report_timing_summary, report_cdc, DRC and utilization results. Investigate exceptions rather than using them to hide a path that should be analyzed.

No universal slack threshold

Version 1 assigned fixed small positive margins to labels such as "comfortable" or "stable". These are not general engineering guarantees. Meet the device and tool timing requirements for the intended operating conditions, with valid constraints, then validate the hardware. Small positive slack neither proves instability nor certifies every asynchronous or functional path.

High utilization and congestion can make closure harder. Inspect the actual critical paths and implementation reports. A module boundary is not inherently a timing defect. Pipelining, placement, fanout management and architecture changes must be justified by reports and checked for latency and functional effects.

Review before generating the release image

  • All expected clocks are present and correctly related.
  • Relevant paths are timed or have a justified exception.
  • Setup, hold and other required checks pass for the selected operating conditions.
  • CDC issues and critical warnings have a recorded disposition.
  • DRC, utilization and resource choices match the intended board.

Hardware validation complements these checks. It does not excuse a known timing violation. Conversely, timing closure cannot establish driver compatibility, protocol correctness or data integrity. Retain both implementation reports and live acceptance evidence for each candidate release.

13. Programming and artifact identity

Keep volatile FPGA configuration separate from nonvolatile flash programming. Programming a configuration memory and loading the new FPGA configuration are distinct operations, although a board tool may perform both. Follow the procedure for the exact board and programmer [R8].

Pre-program checklist

  • Exact board and FPGA identified; approved image matches that target.
  • Flash device, interface, offset and capacity confirmed from board documentation.
  • Image hash checked against the expected artifact.
  • Known working image and recovery procedure available.
  • Other tools that could contend for the same adapter or device stopped.

Do not assume a universal SPI capacity, interface width, bitstream offset or OpenOCD command. Board-specific configuration is part of the programming procedure. An image should not be considered suitable merely because its filename contains the right FPGA size.

After programming

Save the programmer's verification result. Reload using the documented mechanism, then query a running firmware build identifier or another deliberate functional marker. A matching flash readback confirms stored bytes; it does not alone establish that the FPGA loaded those bytes.

Host restart, FPGA reconfiguration, PCIe reset and complete power removal are different events. Some boards remain powered through auxiliary paths. Windows Fast Startup affects the host shutdown path, but its state does not prove whether every board supply was removed. Confirm the actual reset or power behavior required by the board.

For releases, keep target information, build ID, hash, known limitations and rollback instructions together. Keep per-board identifiers and license-binding details private. Public documentation can explain which target is supported without exposing how a commercial implementation derives or enforces identity.

14. Read-only host diagnostics

Start with inventory and event collection. These checks should not modify the device or its drivers. Run them on the host that contains the PCIe card. A programming tool on the operator machine observes a different transport and cannot substitute for host enumeration evidence.

Windows: select the device first

Get-PnpDevice -PresentOnly -Class System |
    Select-Object Status, FriendlyName, InstanceId
# If needed, list all present PCI devices:
Get-PnpDevice -PresentOnly |
    Where-Object InstanceId -like 'PCI\*' |
    Select-Object Status, FriendlyName, InstanceId

Select the exact device instance before collecting details. Do not assume the first match is the FPGA or that an endpoint belongs to the System class. Record the current location and installed driver without replacing it.

$deviceId = Read-Host 'Paste the exact device instance ID'
Get-PnpDeviceProperty -InstanceId $deviceId |
    Where-Object KeyName -match 'Location|Driver|Problem|HardwareIds' |
    Select-Object KeyName, Data
Get-CimInstance Win32_PnPSignedDriver |
    Where-Object DeviceID -eq $deviceId |
    Select-Object DeviceName, DriverProviderName, DriverVersion, InfName

Record the security state without changing it

Get-CimInstance Win32_ComputerSystem |
    Select-Object HypervisorPresent
Get-CimInstance -Namespace root\Microsoft\Windows\DeviceGuard `
    -ClassName Win32_DeviceGuard |
    Select-Object VirtualizationBasedSecurityStatus, SecurityServicesRunning

Use System Information to inspect the reported Kernel DMA Protection state. Keep the limitations in Chapter 6 in mind: these fields are context, not a complete per-device remapping test.

Capture a defined event window

$since = (Get-Date).AddMinutes(-15)
Get-WinEvent -FilterHashtable @{LogName='System'; StartTime=$since} |
    Where-Object Level -in 1,2,3 |
    Select-Object TimeCreated, ProviderName, Id, Message

Retain the full XML for the specific events you investigate. Absence of matching events in a window establishes only that observation, not the absence of every fault. Redact instance IDs, serials and personal paths before sharing a report publicly.

Linux: identify before extended reads

lspci -nn
lspci -t
# Replace the example address with your device:
lspci -s 0000:03:00.0 -vv

Use deeper configuration reads only where appropriate for the device and tool. The pciutils manual warns that some devices can fail when parts of configuration space are read [R9]. Access restrictions or unavailable data must be recorded as such, not converted into supposed register values.

15. Verification matrix and release acceptance

Write the test plan before the change. Define the operation, initial state, input data, expected result, duration and failure criterion. Keep the exact image hash and configuration with every hardware run.

Minimum matrix

  • Build: target, active files, IP generation, DRC, timing and CDC review.
  • Startup: repeated enumeration and driver start on the intended host.
  • Interface: valid and invalid offsets, supported widths, byte enables and side effects.
  • Data: small and large supported transfers, deterministic patterns and full-content comparison.
  • Queueing: concurrency, delayed completion, backpressure and bounded overload.
  • Lifecycle: supported restart, reload, device stop/start and recovery operations.
  • Faults: timeout, unavailable device, cancellation and malformed input in a controlled test harness.
  • Release: exact packaged artifact, clean configuration and known working rollback.

Cover the actual range of supported descriptor counts and transfer sizes. Test boundary conditions explicitly: zero-length or invalid requests where applicable, maximum supported size, boundary crossings, address-width transitions and resource exhaustion. Report unsupported cases as unsupported instead of counting them as passes.

Measure integrity and latency together

Record completed operations, validated bytes, mismatches, failures, retries and recovery attempts. Include elapsed time, transfer size and queue depth with throughput. Compare typical and tail latency when timing affects the application. A short burst benchmark is not an endurance test.

Test the release artifact, not only a development binary with different parameters. A packaging or dependency change can alter the runtime path without an HDL change. Save the test conditions and actual result, including skipped tests.

The exit criterion should be explicit: required checks passed, no unexplained integrity failures, known limits documented and a recovery route available. Do not turn one host's successful run into a claim for all boards, drivers or BIOS versions.

16. Symptom-driven troubleshooting

Use symptoms to choose evidence, not to announce a diagnosis. Record the earliest observable failure and work from the physical and enumeration layers toward the application.

No PCIe enumeration

Check board power, seating, slot allocation, reference clock, reset and the programmed target. Compare the known working image on the same slot. The fact that a USB programmer can identify the FPGA does not prove the PCIe endpoint is configured and linked.

Device present, driver will not start

Record the problem code, resources, actual driver and relevant events. Check the implemented interface and installed OS support. A device description or vendor name is not evidence of a correct driver/interface match.

Data path fails under load

Compare failure thresholds against transfer length, descriptor count, queue depth, stall duration and elapsed time. Inspect integrity, completion accounting, address width and reset events. Do not assume that every large-transfer failure is a single scatter/gather bug.

Device disappears

Preserve logs before reset. Distinguish loss of PCIe enumeration from loss of a child interface or an external management session. Investigate link, power, driver recovery, reset and protocol behavior. Disappearance alone does not prove the hard IP is permanently wedged.

Windows stop error

Save the dump and exact bug-check arguments. For 0x133, Microsoft describes both individual and cumulative DPC/ISR timeout conditions [R10]. Use the dump and associated events to investigate the path. Do not assign a register race or descriptor error solely from a stop-code number.

Firmware change seems absent

Check source selection, active initialization files, generated IP, packaged artifact and running build ID. Verify the image actually loaded. Do not change several caches, drivers and BIOS settings simultaneously: that destroys the comparison needed to identify the cause.

Fix and verify

Reproduce the failure, make one justified change, rerun the failed case and rerun nearby regression cases. A recovery that requires manual reset is a measured recovery, not proof that the underlying defect disappeared. Keep the failed artifact and its conditions for comparison.

17. Support and compatibility workflow

Collect enough information to identify the failing layer without asking customers to disclose secrets. Separate a pre-purchase compatibility review from a technical failure after delivery.

Useful information

  • Board model, FPGA marking and board revision; a clear board photo if needed.
  • Motherboard, CPU, BIOS and operating-system versions.
  • Slot and cabling arrangement, with programming and data ports identified.
  • Tool version, approved build identifier and relevant error text.
  • Whether the device enumerates and which driver is bound.
  • A short reproduction sequence, timestamps and the last known working configuration.

Collect board identifiers needed for an order or support operation through the private ticket system. Public troubleshooting posts should redact customer identity, license information, hardware serials and private paths. Do not ask for passwords, wallet secrets or unrelated files.

Answer only what the evidence supports

"IOMMU is enabled" does not settle compatibility. "The driver is present" does not settle successful DMA. "The test passed" needs the test name and conditions. If a requested configuration has not been checked, explain what information is still required.

Keep prices, warranty wording, supported products and delivery terms in their current official sources. A technical guide should not freeze a temporary discount or an old compatibility claim into permanent advice. Use the Sylnar website and private support for current commercial terms.

Escalation note

Record the symptom, observations, reproduction, candidate explanation and next diagnostic step separately. This prevents an unverified explanation from becoming a customer-facing promise. Never promise permanent nondetection, unrestricted memory access or universal platform compatibility.

18. What changed from version 1

Version 2 retains the engineering focus while replacing assumptions with explicit interface contracts, evidence labels and reproducible verification. It is a revised public reference, not a certification report for a commercial build.

Corrections

  • Replaced the claimed Hyper-V/VBS prerequisite chain with the documented distinction between Kernel DMA Protection, platform support and driver remapping.
  • Removed universal connector, cable and flash-geometry assumptions.
  • Replaced permanent address-latching and synthetic-interrupt recipes with core-documented reset, configuration and interrupt behavior.
  • Corrected asymmetric FIFO depth reasoning and removed fixed nanosecond "stability" thresholds.
  • Removed automatic-success handling for unsupported operations and recipes that discard acknowledged data.
  • Replaced fixed symptom-to-cause claims and undocumented metadata workarounds with evidence-led diagnosis.
  • Removed blanket cache-deletion and host-security-disable instructions.

Additions

  • Clear separation of source implementation, simulation and live hardware evidence.
  • Driver-supplied DMA addresses, mapping lifetime and scatter/gather validation.
  • Explicit CDC, backpressure, reset and simultaneous-update testing.
  • Build manifests, exact-artifact identification, rollback and release acceptance.
  • Read-only host checks and a practical compatibility/support intake.
  • Editable source, a printable HTML edition and a reproducible PDF build.

The public edition deliberately avoids product-specific architecture and private hardware data. It gives readers a way to reason about their own documented design without disclosing a commercial implementation. Review current vendor documentation when applying any example to a new target.

Appendix A. Working checklists

Before changing firmware

  • Save the known working artifact and record the target board.
  • Record the baseline host state and reproduction steps.
  • State the intended change and which tests can detect a regression.
  • Preserve original source and use a separate build directory.

Before reporting a successful test

  • Identify the exact image and configuration.
  • Record operation totals, integrity checks, errors and retries.
  • State duration, host, driver and operating-system version.
  • List skipped cases and the limits of the conclusion.

Before sharing a report

  • Remove customer identifiers, license details, credentials and private paths.
  • Include the actual error and a bounded time window.
  • Keep observations distinct from proposed causes.
  • Share only files relevant to the reported problem.

Appendix B. Glossary

  • BAR: Base Address Register; describes an endpoint resource that the host allocates.
  • BDF: Bus, Device, Function; a function location within the current PCI topology.
  • BRAM: FPGA block memory; budgeted separately from logic resources.
  • CDC: Clock-domain crossing; requires an appropriate transfer and reset protocol.
  • Configuration space: function identification, resource and capability registers.
  • DMA: device access to memory through an operating-system-defined mapping contract.
  • DRC: design-rule checks; part of build acceptance, not a full functional test.
  • FPGA configuration: loading the logic image into the FPGA; distinct from storing an image in flash.
  • IOMMU: hardware for translating and restricting device-visible memory accesses.
  • IOVA: device-visible address interpreted through the applicable I/O mapping.
  • IP: a reusable hardware block with versioned configuration and interface requirements.
  • MSI / MSI-X: distinct message-signaled interrupt mechanisms configured by the host.
  • PERST#: platform PCIe reset signal; its board wiring and effects must be documented.
  • Requester ID: identifier carried by a PCIe requester; correlated with topology for analysis.
  • Scatter/gather: a transfer described by multiple address/length regions.
  • TLP: Transaction Layer Packet; PCIe request, completion or message unit.
  • VBS: Virtualization-Based Security; distinct from the Kernel DMA Protection requirement set.
  • WNS / WHS: setup and hold slack summary metrics; interpreted with complete constraints.
