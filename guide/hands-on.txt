# Lab 1. Choose the device and freeze the build target
This practical sequence creates firmware, implements an example device interface and explains how to extend the same process to a reference peripheral. It is based on public board support and general engineering lessons. It does not disclose a commercial firmware's hardware identity or internal implementation.

There are two distinct outcomes. First, build the public board project and replace its sample BAR implementation with the original register-device example included with this guide. That gives you actual HDL to simulate, integrate and build. Second, use the reference-device workflow in Lab 5 when implementing a different peripheral's interface. The sample register block alone does not emulate a storage, network or other complex controller.

## Step 1: write down your exact board
For the worked build, the public target is CaptainDMA/75t484_x1 in the upstream PCILeech FPGA repository at commit c538c4170678c13f723dc921905fb81ff3c71d8e. Its project script selects xc7a75tfgg484-2. These are public reference-project values, not a statement about Sylnar firmware. A different board must use its own matching project and constraints.

Use a dedicated operator workspace. The commands below assume Git and Vivado 2022.2 are installed, the 75T target is supported by that installation, and commands are run from the indicated directory. The guide source and examples can be cloned separately from the public board project.
```powershell
New-Item -ItemType Directory -Force C:\fpga | Out-Null
Set-Location C:\fpga
git clone https://github.com/ufrisk/pcileech-fpga.git reference
Set-Location reference
git checkout c538c4170678c13f723dc921905fb81ff3c71d8e
git rev-parse HEAD
Get-ChildItem CaptainDMA\75t484_x1
```
Expected: the revision matches the pinned commit and the target directory contains src, ip, vivado_build.tcl and vivado_generate_project_captaindma_75t.tcl. Record any local changes. Do not substitute the similarly named 100T target or assume a board sold as "75T" has the same wiring.

## Step 2: understand the files you will edit
- src/pcileech_75t484_x1_top.sv: board top level and the public project's parameters.
- src/pcileech_pcie_a7.sv: integration of the PCIe core and application paths.
- src/pcileech_tlps128_bar_controller.sv: request routing and sample BAR implementations.
- src/pcileech_tlps128_cfgspace_shadow.sv: the upstream shadow configuration path.

- src/pcileech_75t484_x1_captaindma_75t.xdc: this board's constraints.

Read the source-file list in the generated project. An edited file is useful only if that is the file being compiled. Keep the public reference's licensing notices intact; this guide does not grant a new license for upstream code.

# Lab 2. Build the unchanged firmware first

Start a fresh Vivado Tcl session and change to C:/fpga/reference/CaptainDMA/75t484_x1. Source the upstream generation script. Do not pass unrelated arguments to this script; it parses its Tcl argument list itself.
```tcl
cd C:/fpga/reference/CaptainDMA/75t484_x1
source vivado_generate_project_captaindma_75t.tcl
puts [get_property PART [current_project]]

```
Expected target: xc7a75tfgg484-2. Expected top: pcileech_75t484_x1_top. Review any requested IP upgrade rather than accepting a changed core without noting it. Keep the source revision, tool version and resolved IP configuration with the build record.

## Step 4: synthesize, implement and export
In that same Tcl session, run the public build script, then inspect the run results and write reports. Its final message says "BUILD HOPEFULLY COMPLETED"; that wording is not a verification result.
```tcl
source vivado_build.tcl
puts [get_property STATUS [get_runs synth_1]]
puts [get_property STATUS [get_runs impl_1]]

report_timing_summary -file baseline_timing.rpt

```
The pinned build script copies the image to pcileech_75t484_x1.bin in the target directory. Verify the file exists and inspect the reports before using it. Do not treat a stale file from an earlier run as the output of a failed build.
```powershell
Set-Location C:\fpga\reference\CaptainDMA\75t484_x1
Get-Item .\pcileech_75t484_x1.bin
Get-FileHash .\pcileech_75t484_x1.bin -Algorithm SHA256
Copy-Item .\pcileech_75t484_x1.bin .\baseline-75t.bin
```
The unchanged build establishes that your toolchain can build the selected public project. It does not validate your board until you program and test it using Lab 6. Keep the baseline image separate from later output files.

# Lab 3. Implement and simulate a register device
## Step 5: define the device before writing HDL
The example device occupies the existing public project's BAR0 aperture. It implements a deliberately small 32-bit register interface. Use the existing BAR size and address routing in the pinned project; this lab does not change the endpoint's PCI identifiers or impersonate another manufacturer's product.
- Offset 0x000: read-only example signature, 0x47554944.
- Offset 0x004: read-only example build number, 0x00020001.
- Offset 0x008: read/write scratch register, reset value zero, four byte-enable lanes.
- Offset 0x00C: read-only free-running 32-bit cycle counter, wrapping naturally.
- Other offsets: return zero; writes have no effect.

The module receives decoded BAR requests, not raw TLPs. It returns one response per read, preserves the 88-bit opaque request context and uses two registered stages. Simultaneous read/write of the scratch register returns its previous value. Reset clears the scratch register and pending responses. These choices are the example device's specification.

## Step 6: use the included implementation
The complete module is examples/register-lab/guide_bar.sv. The full source is also printed in the code appendix. It gives each state element one sequential owner, honors byte enables and snapshots response data with its context. The code is an independent teaching example, not a copied product module.

To give the device more registers, add the offset and access semantics to the interface specification first, then implement the decode and matching tests. Do not let an address decode wrap unexpectedly across a smaller aperture. If you change the BAR size, update both the core configuration and address mapping and repeat host resource validation.

## Step 7: run the self-checking simulation
Clone this guide into C:/fpga/guide, or adjust the example paths below to its location. Open the Vivado 2022.2 command prompt so the simulator tools are on PATH. Run in a separate simulation directory.
```powershell
git clone https://github.com/Sylnar/dma-firmware-guide-1.git C:\fpga\guide
New-Item -ItemType Directory -Force C:\fpga\sim | Out-Null
Set-Location C:\fpga\sim
xvlog --sv C:/fpga/guide/examples/register-lab/guide_bar.sv `
           C:/fpga/guide/examples/register-lab/tb_guide_bar.sv
xelab tb_guide_bar -s guide_bar_sim
xsim guide_bar_sim -runall
```
Stop if either compilation or elaboration fails. Expected successful result: GUIDE_BAR_PASS checks=56. The accompanying testbench checks register values, read timing, context preservation, partial and disabled writes, read-only behavior, unknown offsets, consecutive reads, read/write overlap and reset cancellation.

The included example passed these 56 checks in Vivado Simulator 2022.2 when this guide was revised. That establishes the local module behavior exercised by the testbench. The complete upstream design has not been built, programmed or hardware-accepted as part of this documentation revision.

Copy guide_bar.sv into C:/fpga/reference/CaptainDMA/75t484_x1/src. Open src/pcileech_tlps128_bar_controller.sv and locate the existing instance:
```sv
pcileech_bar_impl_zerowrite4k i_bar0(
```

Replace only the module type, leaving that instance's complete port connections intact:
```sv

```
The included module intentionally uses the same names and widths as that upstream implementation contract. Keep the controller's filtering of read/write requests by BAR index. Do not instantiate the new module a second time with the same output nets.

## Step 9: add the source and rebuild
Open the generated project in Vivado. Use these Tcl commands after ensuring the working directory is the target project directory. The testbench is simulation-only and must not enter the synthesis fileset.
```tcl
add_files -norecurse ./src/guide_bar.sv
update_compile_order -fileset sources_1
get_files *guide_bar.sv
reset_run synth_1
launch_runs synth_1 -jobs 4
wait_on_run synth_1
puts [get_property STATUS [get_runs synth_1]]
```
Inspect the synthesis result. Resolve errors such as an unknown module, width mismatch or multiple driver before continuing. Resetting the parent synthesis run invalidates dependent implementation output; launch implementation only after synthesis succeeds.
```tcl
launch_runs impl_1 -to_step write_bitstream -jobs 4
wait_on_run impl_1
puts [get_property STATUS [get_runs impl_1]]
open_run impl_1
report_timing_summary -file register_lab_timing.rpt
report_drc -file register_lab_drc.rpt
report_cdc -file register_lab_cdc.rpt
report_utilization -file register_lab_utilization.rpt
```
The generation script enables binary output. Find the resulting .bin and .bit under pcileech_75t484_x1/pcileech_75t484_x1.runs/impl_1. Copy the new binary to a separate name such as register-lab-75t.bin and record its hash. Do not accidentally flash baseline-75t.bin when testing the new register device.

## Step 10: confirm that the host can reach the BAR path
An instantiated register block is not proof of host accessibility. In the pinned upstream source, BAR0 is configured as a 4 KiB, 32-bit, non-prefetchable memory resource. On-board BAR processing defaults to enabled in pcileech_fifo.sv, and its control reaches the BAR controller through bar_en. Confirm these unchanged public-project settings and the host's actual allocation. Memory Space Enable and resource accessibility must also be valid; a disabled path cannot return the example signature.

Do not drive a configuration signal from a second procedural block just to force access. Maintain the public project's control ownership and do not enable DMA or interrupts as a side effect of a BAR-read test. Readback should be performed through a driver that owns the resource or an isolated development environment, not an arbitrary physical-memory write utility.

# Lab 5. Emulate a reference device, step by step
The register-device lab teaches the mechanics of creating an endpoint. Emulating another peripheral requires a second specification: what that peripheral actually exposes and how its driver uses it. A static configuration dump supplies only part of that information.

## Step 11: choose a reference you can document
Choose a device for which the register and command interface is public, or for which you can establish the required behavior on your own test hardware. Record the exact revision, driver and operating conditions privately. The public guide does not name Sylnar's reference hardware or reproduce its captures.

Define the intended compatibility scope. For a first implementation, specify a limited set of functions and document which operations are unsupported. A network controller that enumerates but cannot exchange packets is not a functioning network-device emulation. Likewise, a driver loading successfully does not prove the device's operational interface works.

## Step 12: capture enumeration and topology
On an appropriate Linux test host, identify the function before capturing more detail. Substitute its actual BDF in the example commands.
```sh
lspci -nn
lspci -t
lspci -s 0000:03:00.0 -vv > reference-decoded.txt
```
If the device supports safe configuration-space reads and your access method permits them, save the required raw configuration range too. Extended reads can affect some devices; consult the pciutils manual and start with the access appropriate to the hardware.
```sh
sudo lspci -s 0000:03:00.0 -xxx > reference-config-256.txt
# Only when appropriate for this device and test setup:
sudo lspci -s 0000:03:00.0 -xxxx > reference-config-extended.txt
```
Capture idle-after-start, active operation and the supported reset/power transitions separately. Include timestamps and driver versions. Keep read errors distinct from valid zero data. Never publish actual private-device dumps, serials or subsystem fingerprints as example files.

## Step 13: turn the capture into a field workbook
Create a row for every implemented field, including its offset, width, reset value, read behavior, write behavior, byte enables, reset domain and source of truth. Add the test that will verify it. Use the public specification to distinguish static declarations, host-programmed controls and live status; a difference between two captures is evidence to investigate, not a complete semantic description.

For example, a read-only identification field must ignore writes; a host-written control must retain allowed bits; a write-one-to-clear event register must clear only the acknowledged bits; and a live status field must track the implemented condition. Reserved fields follow the documented rule for that interface. Keep the reference's private values out of reusable examples.

## Step 14: configure the PCIe core and shadow consistently
In Vivado, open the project's pcie_7x_0 IP customization and review device identity, class, BARs, interrupt support, link parameters and optional capabilities. Use the legally appropriate identifiers for your own design and the resource layout required by the interface you implement. Save and regenerate the core outputs.

For a project that also serves configuration space through a shadow path, inspect which fields the hard IP owns and which requests reach application logic. Update the active configuration initialization and writable-bit definitions accordingly. The pinned public project uses the COE files identified in Lab 1; do not assume that editing a file with a similar name elsewhere changes the compiled design.

Do not copy an entire post-enumeration dump into reset state. Assigned BAR addresses, current interrupt destinations and driver-programmed control values belong to a particular host session. Check the actual host-visible result after building and enumerate the capability chains again.

## Step 15: implement register semantics
Replace sample BAR implementations with modules that implement your field workbook. Start with identification and scratch behavior, then add one functional register group at a time. Use one owner per register and compute an explicit next state when host actions and hardware events overlap.

The following independent example shows an abstract sticky-event register. enabled_write_mask must already include the request's byte enables. Here new events win over same-cycle acknowledgments; choose precedence according to the target interface, not by copying this equation blindly.
```sv
logic [31:0] pending, clear_mask;
assign clear_mask = ack_valid ?
                    (ack_data & enabled_write_mask) : 32'b0;
always_ff @(posedge clk) begin
    if (reset) pending <= 32'b0;
    else pending <= (pending & ~clear_mask) | new_events;
end
```
Test a single event, no-op writes, partial acknowledgments, simultaneous event/acknowledgment and reset. Verify that read-data latency preserves the original request context, as demonstrated in guide_bar.sv. Byte-enable mistakes and context/data misalignment can make a register map look correct in an idle test but fail under normal driver traffic.

## Step 16: implement the functional operation
Trace a complete operation from the host command through device state to completion. Define how the host supplies buffers, when those buffers may be accessed, how many bytes move and which event completes the operation. Implement the actual data movement or functional response; do not return invented success to satisfy the driver.

If the interface uses scatter/gather descriptors, read the actual advertised count and each entry's actual length. Bound the walk to the supported limit. Track per-entry remaining bytes and total operation remaining bytes separately, including a final short fragment. Reject an unsupported count or malformed descriptor before accessing outside the supplied table. Avoid inferring descriptor count from a transfer-size guess.

For requests that need a response, keep the request identity until it is retired or canceled. Test split completions, backpressure, upper address bits and mapping lifetime. Publish no commercial queue limits, arbitration settings or internal routing choices; those values are not needed to explain the general technique.

## Step 17: implement interrupt, reset and error behavior
Generate the completion indication defined by the interface after the required state and data updates are visible. Respect interrupt enable/mask state and use the selected core's request/acceptance handshake. Preserve pending events across temporary backpressure as required by the interface.

Reset must return the device to its specified state and stop or cancel work consistently. Test reset during an outstanding operation, not just after idle. For unsupported commands, implement the documented error result. For timeouts, specify what the host sees and how late responses are handled; do not reuse state while an earlier response could be mistaken for new work.

## Step 18: compare behavior with the reference
Run the same documented operations on the reference and your endpoint under comparable conditions. Compare fields by meaning: host-assigned addresses need not match numerically, whereas resource size and supported semantics must. Compare data results, completions, interrupts, reset behavior and errors as well as enumeration.

Record which features have been simulated and which were observed on hardware. A useful compatibility claim names the reference revision, driver, OS and tested operations in the private engineering record. It does not expose private captures publicly or claim complete equivalence from one successful driver start.

# Lab 6. Program, read back and package the firmware
## Step 19: program the correct image
Use the documented programmer for your exact board. In its interface, detect the FPGA, confirm the target, select register-lab-75t.bin or your reviewed device image, program the intended configuration memory and wait for verification. Follow the board's documented reload or power sequence. Programming a different board, the wrong flash geometry or a stale output is not a valid test of the HDL.

## Step 20: validate the register-device example
On the host, identify the correct endpoint and confirm its BAR resources. Use a test driver that owns the BAR to perform the following 32-bit MMIO operations at BAR0 plus the listed offsets. These are device-register accesses; they are not system-RAM accesses and must not be redirected to a guessed physical address.
- Read 0x000: expect 0x47554944.
- Read 0x004: expect 0x00020001.
- Read 0x008 after reset: expect zero.
- Write 0x11223344 to 0x008, then read back: expect 0x11223344.
- Read 0x00C twice with a delay: expect counter progress, allowing wraparound.
- Write the identification register, then read it: its read-only value must remain unchanged.
- Reload/reset as documented, then confirm the scratch register resets.

On an isolated Linux lab host, the included check_bar_linux.py can use the standard sysfs resource mapping for this exact example device. It stops if a driver owns the device or the example signature/build do not match. First run the read-only mode; use the optional scratch mode only after confirming the exact BDF and expected device. Copy the guide repository to that host and run:
```sh
sudo python3 examples/register-lab/check_bar_linux.py 0000:03:00.0
sudo python3 examples/register-lab/check_bar_linux.py 0000:03:00.0 --test-scratch
```
Expected: the signature/build values above, a changing counter and GUIDE_BAR_HOST_PASS; scratch mode additionally prints SCRATCH_PASS and restores the original scratch value. Access can be unavailable under host policy or with Memory Space Enable clear. Do not change host security policy just to force mapping; use the supported device driver or diagnose the allocation. The Linux host script has not been hardware-run during this guide revision. On Windows use a resource-owning development driver; this Linux sysfs procedure is not a Windows command.

The included HDL testbench verifies the register contract before integration. Hardware readback additionally verifies actual TLP routing, byte order, clocking and the active image. Do not claim a hardware pass from simulator output alone.

## Step 21: package a reproducible release
Retain the source commit, exact target, tool version, parameters, constraints, reports, artifact hash and acceptance results. Include a recovery image and known limitations. Check that the packaged image matches the tested image. Keep source containing private implementation and any reference-device captures outside the public release.

You have now followed the creation sequence: documented interface, HDL implementation, simulation, integration, synthesis, implementation, programming and host verification. For a reference peripheral, the completion milestone is the tested set of functional operations, not merely an altered device description.
